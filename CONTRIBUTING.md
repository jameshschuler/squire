# Contributing to Squire

Thanks for helping out. Squire is a small fan-made companion app for WalkScape, so the process is light. Please read the parts on the WalkScape API, though. The data isn't ours, and access depends on using it well.

## Getting set up

You need Node 24 (see `.node-version`), pnpm 10, and a WalkScape Data API key. Keys are handed out in the "Walkscape Data API" thread on the WalkScape Discord.

```sh
git clone https://github.com/jameshschuler/squire.git
cd squire
cp .env.example .env    # add your key, keep WALKSCAPE_ENV=dev
pnpm install
pnpm dev                # API on :3000, web on :5173
```

The repo has three parts:

- `packages/data-client`: the WalkScape Data API client, with types generated from the API's OpenAPI spec and loaders for whole resources. It will be published to npm, so keep it free of anything Squire-specific and avoid adding runtime dependencies.
- `apps/api`: the Fastify server. It's the only place the API key lives. `src/recipe-book/` turns game data into Squire's recipe book, and `src/character/` reads a player's character export. The web app imports them as `@squire/api/recipe-book` and `@squire/api/character`, so keep both folders free of server code.
- `apps/web`: the React PWA (TanStack Router, Tailwind, shadcn, Lucide).

## Using the WalkScape API

- Develop against the **dev** environment (`WALKSCAPE_ENV=dev`). Prod is for the deployed app.
- The limit is 120 requests a minute per IP. The API server caches game data and only checks `/version` every few minutes. Don't add code that calls the WalkScape API per user request.
- Never commit your key or paste it into an issue, PR or log.
- The API terms allow community tools, but not redistributing the raw dataset. Serve only what the app needs, and keep test fixtures small.
- Keep the WalkScape credit and links on the About page.

## Making a change

1. Branch from `main`: `feature/short-description`, `bugfix/short-description` or `hotfix/short-description`.
2. Make the change, with tests (see below).
3. Run the same checks CI runs:

   ```sh
   pnpm format:check && pnpm lint && pnpm typecheck && pnpm test && pnpm build
   ```

   `pnpm format` fixes formatting.

4. Commit with a prefix: `feat:`, `fix:`, `improvement:`, `docs:`, `refactor:`, `ci:`, `chore:` or `revert:`. A scope is welcome, e.g. `feat(web):` or `fix(data-client):`.
5. Open a PR against `main` with two sections: `## Summary` (what changed and why) and `## Testing` (what you ran and how you checked it).

`main` is protected. Every change lands through a PR, and the **CI passed** check has to be green before merging. Open PRs against `main` rather than stacking them on other branches. Stacked PRs merge into their base branch, not into `main`.

## Dependencies

Dependabot opens weekly update PRs. Patch and minor updates merge on their own once **CI passed** is green. Major updates wait for a human to review them.

## Code style

ESLint and Prettier cover formatting and most rules. Beyond that:

- **Keep it simple.** Use plain functions and data. Add a class, abstraction or option only when a second real use needs it.
- **Few comments.** Add one only when the logic is genuinely hard to follow.
- **Always use braces** on `if` statements, even one-liners. Lint enforces this.
- **Use the game's words.** Recipe, material, service, tier, location: one name per idea, everywhere.
- **Keep game rules out of the UI.** Recipe logic belongs in `apps/api/src/recipe-book/` (or in the data client when any app could use it), and components just render it.

In `apps/web`:

- One component per file, named after the component, and under about 150 lines.
- Components are grouped by feature in `src/components/` (`recipes/`, `layout/`, `shared/`). Generated shadcn primitives live in `src/components/ui/`.
- Pure helpers go in `src/lib/` (with tests), hooks in `src/hooks/`, contexts in `src/contexts/`.
- `src/routeTree.gen.ts` is generated by the router plugin. Don't edit it.
- App icons (favicon, PWA, Apple touch, maskable) are generated from `public/icon.svg`. Edit the SVG, then run `pnpm --filter @squire/web generate-icons` and commit the results. Don't edit the PNGs or `favicon.ico` by hand.

## Tests

Every change ships with tests. New logic gets unit tests, and a bug fix gets a test that fails without the fix.

- Test behaviour, not internals. Assert on inputs, outputs and what the user sees.
- Mock only the edges: the network, time and storage.
- Cover empty, boundary and error cases, not just the happy path.

The `*.live.test.ts` files run against the real dev API, but only when `WALKSCAPE_API_KEY` is set in your shell. CI skips them. `packages/data-client/test/contract.live.test.ts` checks real responses from every resource against the API spec, so run it after regenerating the types.

`.github/workflows/api-contract.yml` runs that check every Monday, and also regenerates the types and fails if the spec has changed. It needs the `WALKSCAPE_API_KEY` repository secret. You can also start it by hand from the Actions tab.

## Updating the data client's types

The data client's types come from the API's OpenAPI spec. When the API changes, run `pnpm --filter @walkscape-community/data-api-client generate`. It rewrites `packages/data-client/src/generated/`; never edit those files by hand. Then run the checks: if a search filter or a field the code uses changed, typecheck shows where.

## Publishing the data client

`packages/data-client` is published to npm as `@walkscape-community/data-api-client`. Releases go out from CI:

1. In a PR, bump `version` in `packages/data-client/package.json` and add a `CHANGELOG.md` entry.
2. After it merges, tag the PR's merge commit and push the tag: `git fetch origin && git tag data-client-vX.Y.Z <merge-commit> && git push origin data-client-vX.Y.Z`. The merge commit is on the PR page, or run `gh pr view <number> --json mergeCommit -q .mergeCommit.oid`.
3. `.github/workflows/release-data-client.yml` checks that the tag matches the version, runs the data client's typecheck, tests and build, packs it and checks the packed copy, then stages it on npm through trusted publishing (no npm token) and creates a GitHub Release.
4. Approve the staged version on npmjs.com (the package's **Staged Packages** tab) or with `npm stage approve <stage-id>`. Approval needs your 2FA code, and nothing is installable until then.

In the repo, `exports` points at the TypeScript source. `pnpm pack` swaps in the built `dist/` paths from `publishConfig`, which is why the workflow packs with pnpm before publishing with npm.

Tests and the API server use the source, so they can't catch a broken package. `scripts/check-package.mjs` does: it installs a packed tarball into an empty folder, type-checks a small consumer against it and calls the client with a fake `fetch`. CI runs it on every PR, as part of the Build job. To run it yourself:

```sh
cd packages/data-client
out=$(mktemp -d)
pnpm build && pnpm pack --pack-destination "$out"
node scripts/check-package.mjs "$out"/*.tgz
```

Doc comments on the data client's exports are its documentation in editors, so keep them accurate when you change an export.

## Reporting bugs and security issues

Open an issue for bugs and ideas. For a security problem, don't open a public issue. Contact the maintainer privately through GitHub instead.

If you hit something wrong in the game data itself, report it in the Data API thread on Discord.
