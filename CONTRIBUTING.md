# Contributing to Squire

Thanks for helping out. Squire is a small fan-made companion app for WalkScape, so the process is light. Please read the parts on the WalkScape API, though. The data isn't ours, and access depends on using it well.

## Getting set up

You need Node 24 (see `.node-version`), pnpm 10, and a WalkScape Data API key. Keys are handed out in the "Walkscape Data API" thread on the WalkScape Discord.

```sh
git clone https://github.com/jameshschuler/squire.git
cd squire
cp .env.example .env    # add your key, keep WALKSCAPE_ENV=dev
pnpm install
pnpm dev                # API on :3000, web on :5173
```

The repo has three parts:

- `packages/sdk`: the WalkScape Data API client and game helpers. It will be published to npm, so keep it free of anything Squire-specific and avoid adding runtime dependencies.
- `apps/api`: the Fastify server. It's the only place the API key lives.
- `apps/web`: the React PWA (TanStack Router, Tailwind, shadcn, Lucide).

## Using the WalkScape API

- Develop against the **dev** environment (`WALKSCAPE_ENV=dev`). Prod is for the deployed app.
- The limit is 120 requests a minute per IP. The API server caches game data and only checks `/version` every few minutes. Don't add code that calls the WalkScape API per user request.
- Never commit your key or paste it into an issue, PR or log.
- The API terms allow community tools, but not redistributing the raw dataset. Serve only what the app needs, and keep test fixtures small.
- Keep the WalkScape credit and links in the app footer.

## Making a change

1. Branch from `main`: `feature/short-description`, `bugfix/short-description` or `hotfix/short-description`.
2. Make the change, with tests (see below).
3. Run the same checks CI runs:

   ```sh
   pnpm format:check && pnpm lint && pnpm typecheck && pnpm test && pnpm build
   ```

   `pnpm format` fixes formatting.

4. Commit with a prefix: `feat:`, `fix:`, `improvement:`, `docs:`, `refactor:`, `ci:`, `chore:` or `revert:`. A scope is welcome, e.g. `feat(web):` or `fix(sdk):`.
5. Open a PR against `main` with two sections: `## Summary` (what changed and why) and `## Testing` (what you ran and how you checked it).

`main` is protected. Every change lands through a PR, and the **CI passed** check has to be green before merging. Open PRs against `main` rather than stacking them on other branches. Stacked PRs merge into their base branch, not into `main`.

## Dependencies

Dependabot opens weekly update PRs. Patch and minor updates merge on their own once **CI passed** is green. Major updates wait for a human to review them.

## Code style

ESLint and Prettier cover formatting and most rules. Beyond that:

- **Keep it simple.** Use plain functions and data. Add a class, abstraction or option only when a second real use needs it.
- **Few comments.** Add one only when the logic is genuinely hard to follow.
- **Always use braces** on `if` statements, even one-liners. Lint enforces this.
- **Use the game's words.** Recipe, material, service, tier, location: one name per idea, everywhere.
- **Keep game rules out of the UI.** Recipe logic belongs in the SDK, and components just render it.

In `apps/web`:

- One component per file, named after the component, and under about 150 lines.
- Components are grouped by feature in `src/components/` (`recipes/`, `layout/`, `shared/`). Generated shadcn primitives live in `src/components/ui/`.
- Pure helpers go in `src/lib/` (with tests), hooks in `src/hooks/`, contexts in `src/contexts/`.
- `src/routeTree.gen.ts` is generated by the router plugin. Don't edit it.
- App icons (favicon, PWA, Apple touch, maskable) are generated from `public/icon.svg`. Edit the SVG, then run `pnpm --filter @squire/web generate-icons` and commit the results. Don't edit the PNGs or `favicon.ico` by hand.

## Tests

Every change ships with tests. New logic gets unit tests, and a bug fix gets a test that fails without the fix.

- Test behaviour, not internals. Assert on inputs, outputs and what the user sees.
- Mock only the edges: the network, time and storage.
- Cover empty, boundary and error cases, not just the happy path.

`packages/sdk/test/live.test.ts` runs against the real dev API, but only when `WALKSCAPE_API_KEY` is set in your shell. CI skips it.

## Publishing the SDK

`packages/sdk` is published to npm as `@jameshschuler/walkscape-sdk`. Publish with `pnpm publish` from that folder, not `npm publish`. In the repo, `exports` points at the TypeScript source, and only pnpm swaps in the built `dist/` paths from `publishConfig`. `prepublishOnly` rebuilds before each publish.

Doc comments on the SDK's exports are its documentation in editors, so keep them accurate when you change an export.

## Reporting bugs and security issues

Open an issue for bugs and ideas. For a security problem, don't open a public issue. Contact the maintainer privately through GitHub instead.

If you hit something wrong in the game data itself, report it in the Data API thread on Discord.
